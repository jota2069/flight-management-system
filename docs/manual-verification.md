# Локальный запуск и ручная проверка

## 1. Данные и секреты
Никакие миграции этого изменения не применялись к вашей рабочей БД. Интеграционные
проверки работали только с отдельным временным PostgreSQL.

Если Docker volume уже содержит данные:
1. Сделайте резервную копию и отдельно проверьте восстановление.
2. Остановите старые версии Web/API. Не запускайте старый и новый писатели одновременно.
3. Задайте действующие данные подключения. POSTGRES_PASSWORD влияет на инициализацию
   нового volume, но НЕ меняет пароль пользователя в существующем PostgreSQL.
   Смену ранее использовавшегося demo-пароля выполните отдельно штатными средствами
   PostgreSQL; не рассчитывайте на изменение переменной Compose.
4. Проверьте SQL миграций и старые данные. API применяет миграции до приёма запросов.
   BookingConstraints остановится при дублях мест, превышении вместимости, некорректных
   ценах/номерах мест или неположительной вместимости. Записи не удаляются и владельцы
   не назначаются. Не обходите эту проверку удалением истории миграций.
5. После ошибки анализируйте данные с резервной копией. IdentityAndOwnership могла уже
   примениться отдельно; это добавляет NULL-владельцев, но не присваивает их пользователям.

Для НОВОГО локального окружения можно получить случайные значения без записи в файлы:
```bash
export POSTGRES_PASSWORD="$(openssl rand -hex 32)"
export GRAFANA_ADMIN_PASSWORD="$(openssl rand -hex 32)"
docker compose up --build -d db cache api
docker compose logs api
# После сообщения об успешном запуске API:
docker compose up --build -d web proxy
```
Сохраните новые значения в менеджере секретов до закрытия shell. Не запускайте
docker compose config без --quiet при реальных секретах: вывод содержит подстановки.
Не удаляйте volumes существующих БД. Эти команды здесь приведены как инструкция;
создание аккаунтов и изменение ваших данных автоматически не выполнялось.

## 2. Аккаунты и тестовый рейс
1. Откройте http://localhost:8080/Register. Создайте Alice и Bob с разными сильными
   паролями (12–128 символов). Не используйте реальные персональные данные.
2. После миграций создайте нового администратора:
   docker compose exec web dotnet FlightManagement.Web.dll --create-admin YOUR_NEW_ADMIN_LOGIN
   Пароль вводится без эха, не аргументом команды и не через историю shell.
3. Войдите администратором, откройте /Admin и создайте синтетический рейс с будущими
   датами, временем прибытия позже вылета и вместимостью 2–3. Даты приложения — UTC.
4. Откройте Alice и Bob в отдельных профилях браузера/приватных окнах, а не двух
   вкладках с одним cookie-хранилищем. Сессии host-only, но cookie не изолируются по порту.

## 3. Владение и CSRF
1. Alice бронирует билет: имя Synthetic, фамилия Tester, документ TEST-ONLY,
   email synthetic@example.invalid, телефон TEST, дата рождения 2000-01-01,
   место 1A, положительная учебная цена. Это НЕ платёж.
2. Alice видит свой билет; Bob не видит его в списке. При пустом списке отображается
   «У вас пока нет билетов», а не общий список.
3. В инструментах браузера воспроизведите запросы GET/PUT/DELETE к ID Alice с cookie Bob.
   Ожидается 404; данные не меняются. /api/Passengers также ограничен владельцем.
4. Получите собственный токен через GET /api/security/csrf. Unsafe API-запросы требуют
   и cookie, и X-CSRF-TOKEN. Без токена/с чужим токеном — 400; с чужим Origin — 403.
   Удаление hidden __RequestVerificationToken из Razor POST тоже даёт 400.
5. /Admin и изменение расписания недоступны обычному пользователю.
   Старые ownerless-записи видит только Admin; совпадение имён/email не меняет владельца.
6. После выхода через форму повторное использование старой session cookie в API
   даёт 401: обновлён security stamp, отозваны все сессии этого аккаунта.
   Для приватных API 401/403 — коды ответа, не HTML со статусом 200.

## 4. Места и кеш
1. Отправьте два параллельных бронирования последнего свободного места. Ожидается
   один 201, другой 409. Число билетов не превышает TotalSeats.
2. Повторите одно место с разным регистром и пробелами: 1A / 1a. Второе не создаётся.
   В БД есть уникальный индекс на рейс и вычисляемое нормализованное место.
3. Уменьшение вместимости ниже числа билетов и удаление рейса/пассажира с билетами
   дают 409. Отмена билета освобождает место; перенос резервирует место в новом рейсе.
4. Отключите только cache-сервис (docker compose stop cache), не db.
   GET /api/Flights и GET /api/Flights/{id} продолжают читать PostgreSQL; возможна
   задержка до Redis timeout. Затем docker compose start cache.
5. Бронирование/изменение/отмена и изменение рейсов транзакционно увеличивают
   CacheRevisions.Version. Старые Redis-ключи недоступны новым чтениям и истекают за 5 минут.
   Публичное расписание не содержит tickets/crewAssignments и данных пассажиров.

## 5. Запуск без Docker
Оба хоста должны использовать одну БД, одинаковые PUBLIC_ORIGIN и KEY_RING_PATH.
KEY_RING_PATH — абсолютный путь; новая Unix-директория создаётся 0700, небезопасные
права существующей директории вызывают ошибку без автоматического chmod.
CONNECTION_STRING обязателен, дефолтного пароля нет. API_BASE_URL Web указывает
на доверенный внутренний API. Выполните API-миграции до запуска Web.
В production API_BASE_URL обязан использовать HTTPS с доверенным сертификатом:
Web откажется стартовать с HTTP/default URL. Не отключайте проверку сертификата
или Secure antiforgery cookie ради HTTP-промежуточного соединения.
Для HTTPS reverse proxy задайте точные TrustedProxies__0 и далее.
Публично оставьте один origin; не включайте CORS credentials для произвольных сайтов.

Глобальный dotnet-ef может быть другой версии. Используйте manifest:
```bash
dotnet tool restore
dotnet ef migrations script --idempotent --project src/FlightManagement.Api
```
Не выводите реальные connection strings в отчёты. Не делайте откат Identity-миграции
на рабочей БД без плана восстановления: он удаляет таблицы аккаунтов/метаданные владельцев.
